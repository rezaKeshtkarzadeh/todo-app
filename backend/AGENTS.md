2. **SQLAlchemy 2.0 Async Syntax:** You MUST use SQLAlchemy 2.0 style queries. Use `select()`, `insert()`, `update()` with `await session.execute(...)` and `session.scalars()`. DO NOT use legacy `session.query(...)`.

5. **No Blind Exception Catching:** Never use bare `except:` or catch `Exception` blindly. Handle specific exceptions and map them to the defined API Error Contract.

## 5. Device

### `devices`

A Device represents a client/device associated with a user.

**Identification contract (binding, defined in `../AGENTS.md` section 7):**

* The Device `id` is a UUIDv4 generated by the frontend and stored in its `localStorage`.
* It arrives on every request through the header `X-Device-Id`.
* A dependency (`dependencies/device.py`) parses and validates it. Missing header â†’ `DEVICE_ID_MISSING` (HTTP 400). Malformed UUID â†’ `DEVICE_ID_INVALID` (HTTP 400).
* The header is **NOT** an authentication factor. It is client-supplied and forgeable. Never make an authorization decision based on it, and never treat a matching `X-Device-Id` as proof of anything.
* Do not implement browser fingerprinting.

Fields:

| Field        | Type           | Requirements                   |
| ------------ | -------------- | ------------------------------ |
| id           | UUID           | Primary key (client-supplied)  |
| user_id      | UUID           | FK â†’ users.id                  |
| name         | String/null    | Optional descriptive name      |
| user_agent   | String/null    | Optional, captured server-side |
| created_at   | Timestamp      | Server-generated               |
| last_seen_at | Timestamp/null | Updated on login and refresh   |
| revoked_at   | Timestamp/null | Device-level revocation        |

Because `id` is client-supplied, device lookup MUST always be scoped by `(id, user_id)`. A `device_id` presented by a different user creates a separate Device row owned by that user. Devices are never shared between users.

A device-management **UI is required** (implemented in the frontend). The backend must expose the API in section 22.c.

## 7. Refresh Token

### `refresh_tokens`

| Field           | Type           | Requirements                   |
| --------------- | -------------- | ------------------------------ |
| id              | UUID           | Primary key / token identifier |
| session_id      | UUID           | FK â†’ sessions.id               |

| token_hash      | String         | Argon2 hash of token secret    |
| issued_at       | Timestamp      | Server-generated               |

| used_at         | Timestamp/null | Set when consumed              |
| revoked_at      | Timestamp/null | Set when revoked               |
| replaced_by_id  | UUID/null      | Points to replacement token    |

### Token Format

```text
token_id.secret
```

* `token_id` identifies the database record;
* `secret` is cryptographically random;
* only the secret portion is stored, through a one-way Argon2 hash;
* the raw secret must never be stored in PostgreSQL.

The token ID exists to allow direct lookup without scanning all Refresh Token hashes. Security still depends entirely on the random secret.

### Argon2

Argon2 must be used for Refresh Token hashing. Do not replace it with plain SHA-256, MD5, reversible encryption, or plaintext storage.

The raw Refresh Token must only exist temporarily during the request lifecycle.

## 10. Refresh Token Reuse Detection

If a Refresh Token that has already been used, revoked, or replaced is presented again, treat it as token reuse.

The backend must:

1. record a Security Log (`REFRESH_TOKEN_REUSED`);
2. revoke the associated token family;
3. revoke the associated Session;
4. reject the request with HTTP 401 and `AUTH_REFRESH_TOKEN_REUSED`;
5. clear authentication cookies.

Do not silently issue another token after reuse detection.

---

## 11. Concurrent Refresh Protection

The same Refresh Token must not be successfully consumed twice.

```text
Token is unused
      â†“
atomically mark as used
      â†“
create replacement
```

Use a conditional `UPDATE ... WHERE used_at IS NULL AND revoked_at IS NULL` and check the affected row count, or an equivalent `SELECT ... FOR UPDATE` transaction. Do not rely only on application-level Python checks.

## 12. `POST /auth/send-otp`

Input:

```json
{ "phone_number": "..." }
```

Behavior:

1. Validate and normalize the phone number.
2. Apply the send cooldown (section 13).
3. Generate a cryptographically secure 4-digit OTP (`secrets`, never `random`).
4. Store it in Redis under `otp:{phone_number}` together with an attempt counter.
5. Set TTL to approximately 120 seconds.
6. For testing only, print the OTP to the console.
7. For testing only, include the OTP in the API response.
8. Record `OTP_REQUESTED` in the Security Log (never the code itself).

```json
{ "message": "OTP generated.", "otp_debug": "1234" }
```

The debug OTP must be clearly marked as testing-only behavior and gated on `ENV != production`. Do not integrate a real SMS provider.

---

## 13. OTP Rate Limiting and Attempt Limits

Two independent protections are required.

### Send cooldown

A phone number should not be able to request new OTPs continuously. A simple Redis-based cooldown of approximately **30 seconds** between requests is sufficient. Violations return HTTP 429 with `AUTH_OTP_RATE_LIMITED`.

### Verification attempt limit

A stored OTP may be submitted incorrectly a **MAXIMUM OF FIVE (5) TIMES**.

* Keep a counter in Redis alongside the code, e.g. `otp_attempts:{phone_number}`, with the same TTL as the code.
* Increment atomically (`INCR`) on each failed verification.
* On the fifth failure, **delete the OTP** and return HTTP 429 with `AUTH_OTP_MAX_ATTEMPTS`. The user must request a new code.
* A successful verification clears both the code and the counter.
* Record `OTP_VERIFICATION_FAILED` per failure and a distinct `OTP_MAX_ATTEMPTS_REACHED` event on lockout.

A 4-digit code without this limit is trivially brute-forceable. This rule is not optional. Do not build a complex distributed rate-limiting system.

## 14. `POST /auth/verify-otp`

Input:

```json
{ "phone_number": "...", "code": "1234" }
```

Requires the `X-Device-Id` header.

Behavior:

1. Read the OTP from Redis. Reject with `AUTH_OTP_EXPIRED` if absent.
2. Compare the submitted code using a constant-time comparison.
3. On mismatch, increment the attempt counter and apply section 13.
4. Delete the OTP and attempt counter after successful verification.
5. Find or create the User.
6. Find or create the Device scoped by `(X-Device-Id, user_id)`; update `user_agent` and `last_seen_at`.
7. Create a Session.
8. Create the initial Refresh Token Family.
9. Create the first Refresh Token and hash its secret with Argon2.
10. Create the Access Token including the session identifier.
11. Set authentication cookies and a fresh `csrf_token` cookie.
12. Record `LOGIN_SUCCESS` in the Security Log.

Neither token is returned in the JSON response.

## 15. Access Token

The Access Token is a JWT containing at minimum:

`sid` is required so that request handling can resolve the current Session without a Refresh Token, which the session-management UI depends on.

Additional identifiers may be included when useful, but unnecessary claims should not be added. The signing secret and algorithm must come from configuration. Default algorithm `HS256`. Default lifetime approximately **15 minutes**.

## 18. `POST /auth/refresh`

Requires CSRF. The endpoint must:

1. Read the Refresh Token cookie.
2. Parse its token identifier and secret.
3. Look up the Refresh Token.
4. Verify the Session (exists, not revoked, not expired).
5. Verify expiration/revocation state of the token.
6. Verify the Device where applicable.
7. Verify the secret with Argon2.
8. Atomically consume the current token.
9. Create a replacement token in the same token family.
10. Issue a new Access Token.
11. Set replacement cookies.
12. Update `sessions.last_used_at` and `devices.last_seen_at`.
13. Record `REFRESH_SUCCESS` in the Security Log.

If the Refresh Token is invalid, expired, revoked, or otherwise unusable: return HTTP 401, clear authentication cookies, do not issue new tokens.

If the Session was revoked (for example by a revocation from another device), return HTTP 401 with `AUTH_SESSION_REVOKED` so the frontend can distinguish it from an ordinary expiry.

Reuse detection follows section 10.

---

## 19. `POST /auth/logout`

Requires CSRF. Logout should:

1. Identify the current Session from the Refresh Token/session context.
2. Revoke the Session.
3. Revoke its active Refresh Token family.
4. Clear `access_token`, `refresh_token`, `csrf_token`.
5. Record `LOGOUT` in the Security Log.

Logout must be idempotent and safe to repeat. Do not expose whether a session existed to an unauthenticated caller: always return the same success shape.

---

## 20. `GET /auth/csrf-token`

Generate a cryptographically random CSRF token and set the `csrf_token` cookie (not HttpOnly, Secure in production, SameSite=Lax).

The frontend calls this endpoint during application initialization. The endpoint does not return an authentication credential and must not require authentication.

## 21. Current User Dependency

A reusable dependency should:

1. Read the Access Token cookie.
2. Verify the JWT signature.
3. Validate expiration.
4. Extract the user ID and session ID.
5. Load the user.
6. Load the Session and confirm it is neither revoked nor expired.
7. Return the authenticated user together with the current session ID.

Invalid or missing authentication results in HTTP 401 `AUTH_UNAUTHENTICATED`. A revoked or expired Session results in HTTP 401 `AUTH_SESSION_REVOKED`, even when the JWT itself is still cryptographically valid. Access Tokens are short-lived but revocation must take effect within that window for anything session-related.

Never trust a user ID or device ID supplied by the frontend for authorization.

---

## 22. CSRF Dependency

State-changing authenticated requests must validate the `X-CSRF-Token` header against the `csrf_token` cookie, using a constant-time comparison.

Missing token â†’ HTTP 403 `CSRF_TOKEN_MISSING`. Mismatch â†’ HTTP 403 `CSRF_TOKEN_INVALID`. Both record `CSRF_FAILURE` in the Security Log.

CSRF validation applies to authenticated `POST`, `PUT`, `PATCH`, `DELETE` requests.

OTP initiation and OTP verification are exceptions because they do not depend on an existing authenticated browser session. Refresh, logout, all profile endpoints, and all session/device revocation endpoints require CSRF protection.

## 22.a Profile: Avatar

### `POST /profile/avatar`

Requires authentication and CSRF. Accepts `multipart/form-data` with a single image file.

* Allowed content types: `image/jpeg`, `image/png`, `image/webp`. Anything else â†’ HTTP 400 `PROFILE_AVATAR_INVALID_TYPE`.
* Maximum size: **5 MB**. Larger â†’ HTTP 413 `PROFILE_AVATAR_TOO_LARGE`.
* Do not trust the client-provided `Content-Type` or file extension. Verify the actual image by decoding its header with Pillow, and reject anything that does not parse as one of the allowed formats.
* Generate the stored filename yourself (`{user_id}/{uuid4}.{ext}`). Never use the client-supplied filename, and never interpolate it into a path.
* Store under the configured uploads directory and save the **relative** path in `users.avatar_path`.
* Replacing an avatar should remove or orphan the previous file deterministically; do not leave the database pointing at a missing file.
* Record `AVATAR_UPDATED` in the Audit Log.
* Serve uploads through a dedicated static mount (e.g. `/uploads`) with the directory coming from configuration.

Return the new avatar path/URL in the response body.

## 22.b Profile: Phone Number Change

A strict, stateful 2-step process. All four endpoints require authentication and CSRF.

1. `POST /profile/phone/request-current` â€” send an OTP to the user's current phone. Subject to the same cooldown and attempt rules as login OTPs.
2. `POST /profile/phone/verify-current` â€” verify that OTP. On success, issue a short-lived opaque `phone_change_token` (cryptographically random) and store it in **Redis** keyed to the user, with a TTL of approximately **10 minutes**. Return the token in the response body. It is a step-up credential, not an authentication credential, and it is never set as a cookie.
3. `POST /profile/phone/request-new` â€” requires a valid `phone_change_token` and the new phone number. Validate that the new number is not already in use (`PROFILE_PHONE_ALREADY_IN_USE`) and is not the current number (`PROFILE_PHONE_SAME_AS_CURRENT`). Send an OTP to the new number.
4. `POST /profile/phone/verify-new` â€” requires the `phone_change_token`, the new phone number, and the new OTP. On success, update the user's phone number, invalidate the `phone_change_token`, and delete both OTPs.

An invalid, expired, or already-consumed `phone_change_token` â†’ HTTP 403 `PROFILE_PHONE_CHANGE_TOKEN_INVALID`.

The token must be bound to the authenticated user and to the requested new phone number once step 3 has run. Presenting it for a different number must fail.

Record `PHONE_CHANGE_REQUESTED`, `PHONE_CHANGE_CURRENT_VERIFIED`, and `PHONE_CHANGE_COMPLETED` in the Security Log, and `PHONE_CHANGED` in the Audit Log. Never log the OTPs or the token.

Changing the phone number does not revoke sessions.

## 22.c Device & Session Management API

All endpoints require authentication. Revocations require CSRF. Everything is scoped to the authenticated user, and any ID belonging to another user returns **404** (`DEVICE_NOT_FOUND` / `SESSION_NOT_FOUND`), never 403.

| Method | Path                                 | Behavior                                            |
| ------ | ------------------------------------ | --------------------------------------------------- |
| GET    | `/security/devices`                  | Devices with their active Sessions nested underneath |
| DELETE | `/security/sessions/{id}`            | Revoke one session                                  |
| DELETE | `/security/devices/{id}/sessions`    | Revoke all sessions for one device                   |
| DELETE | `/security/sessions`                 | **Global logout:** revoke all sessions, all devices  |

`GET /security/devices` returns, per device: `id`, `name`, `user_agent`, `created_at`, `last_seen_at`, and its active sessions with `id`, `created_at`, `last_used_at`, `expires_at`, and a boolean `is_current` computed from the `sid` claim of the current Access Token. Never return token values, hashes, or token IDs.

**Global logout revokes every session including the current one.** After it succeeds, clear `access_token`, `refresh_token`, and `csrf_token` on the response so the calling client is logged out immediately.

Revoking a session must also revoke its Refresh Token family, otherwise a live refresh token could resurrect access.

If the revoked set includes the current session (single-session revoke, device revoke, or global logout), clear the authentication cookies on that response too.

Every revocation records `SESSION_REVOKED` in the Security Log with the scope (`single` / `device` / `global`) in metadata.

## 29. API Error Contract

All controlled API errors use:

```json
{
  "error": {
    "code": "AUTH_INVALID_OTP",
    "message": "The OTP is invalid or has expired.",
    "details": null,
    "request_id": "..."
  }
}
```

Validation errors use the same envelope:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid fields.",
    "details": { "phone_number": ["Invalid phone number format."] },
    "request_id": "..."
  }
}
```

FastAPI's default validation/error handlers MUST be overridden so that `RequestValidationError`, `HTTPException`, and unhandled exceptions all produce this envelope. Error construction belongs in one place (`core/errors.py`). Internal exception details must never be returned to clients.

## 32. Transactions

Operations that must succeed or fail together belong in one transaction:

```text
Refresh Token consumption + replacement creation
Task mutation + Audit Log
Session revocation + token family revocation
Phone number update + Audit Log
```

Avoid unnecessarily long transactions. Redis operations are not a substitute for PostgreSQL transactions and cannot participate in them: order operations so a Redis failure cannot leave PostgreSQL inconsistent.

---

## 33. CORS

CORS must allow only the configured frontend origin, with `allow_credentials=True`. Never use `allow_origins=["*"]` with credentials enabled.

`X-CSRF-Token` and `X-Device-Id` must be present in `allow_headers`, otherwise the browser preflight will fail.

The frontend origin must come from configuration.

`.env.example` should contain at least:

```text

JWT_ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=15
REFRESH_TOKEN_EXPIRE_DAYS=7

OTP_TTL_SECONDS=120
OTP_RESEND_COOLDOWN_SECONDS=30
OTP_MAX_ATTEMPTS=5
PHONE_CHANGE_TOKEN_TTL_SECONDS=600

AVATAR_MAX_BYTES=5242880
UPLOADS_DIR=./uploads

FRONTEND_ORIGIN=
```

Secrets must not be committed. `JWT_SECRET` must have sufficient entropy and must never use a sample value in a real environment.

## 35. Redis Keys

```text
otp:{phone_number}
otp_attempts:{phone_number}
otp_cooldown:{phone_number}
phone_change:{user_id}
```

Additional Redis keys should only be introduced when they solve a concrete short-lived data problem. Do not duplicate PostgreSQL authentication state in Redis.

## 36. Alembic

Alembic must manage the database schema. The initial migration must create:

```text
users
devices
sessions
refresh_tokens
tasks
security_logs
audit_logs
```

Foreign keys must enforce ownership relationships with appropriate cascading. Indexes should exist for token lookup, session lookup by user and device, user-scoped task lookup, and audit/security queries. Do not add indexes without a reason.

---

## 37. Backend Design Principles

Prefer explicit service boundaries, small functions, FastAPI dependency injection, SQLAlchemy transactions, Pydantic schemas at API boundaries, centralized security utilities, centralized cookie configuration, and centralized API error construction.

Avoid generic repository abstractions without concrete need, excessive service layers, global mutable state, business logic inside route definitions, and duplicated authentication logic.

---

## 38. Out of Scope

Do not implement unless explicitly requested:

* real SMS delivery;
* SMS provider SDKs;
* email providers;
* external logging platforms;
* distributed tracing platforms;
* advanced device fingerprinting;
* password authentication;
* OAuth/social login;
* background job infrastructure;
* microservices;
* event sourcing;
* CQRS;
* advanced fraud detection;
* server-side storage of theme/locale preferences.

Note: session and device management (API **and** UI) is explicitly **IN** scope. Earlier revisions of this document listed session-management UI as out of scope; that is no longer the case.

## 39. Backend Testing Protocol

* **Framework:** `pytest`, `pytest-asyncio`, and `httpx` `AsyncClient`.
* **Database:** a separate test database. Each test runs in an isolated transaction that rolls back afterwards.
* **Mocking:** Redis is mocked (`fakeredis` or an equivalent) for speed and determinism. Avatar uploads write to a temporary directory, never the real uploads dir.
* **Required coverage:**
  * OTP attempt limit: five failures destroy the code and return `AUTH_OTP_MAX_ATTEMPTS`.
  * Refresh rotation happy path across several generations.
  * Refresh reuse: family and session revoked, HTTP 401 `AUTH_REFRESH_TOKEN_REUSED`, cookies cleared.
  * Concurrent refresh: two parallel requests with the same token, exactly one succeeds.
  * Cross-user access: another user's task, session, and device all return 404.
  * CSRF: missing and mismatched header on every protected verb.
  * Global logout revokes the current session and clears cookies.
  * Every custom error code returns the expected HTTP status and JSON envelope.
